## The core gap

The R4/R7 application engine (eligibility gates, planning, worker lifecycle, retry/dead-letter, authorization-withdrawal safety net, action-required pause/resume) is real, tested, and correct, and MP-W1 now gives it a real, manually-runnable entry point (`npm run worker:applications`) — but nothing schedules that command automatically (no cron, no CI job, no client trigger) and no client or Express route ever calls `planApplication` directly either, so no real candidate has actually had an `application_plan`/`application_attempt` created for them yet. `ApplicationsPanel`/`ActionRequiredPanel` are fully wired for *reading* but have nothing real to show until the worker is actually scheduled and a real candidate clears every gate. Real ATS submission is additionally blocked on an external employer relationship (see prior session's Greenhouse integration-readiness analysis) — `resolveApplicationAdapter` has no real per-source case (MP-A1 gave the interface a real capability model — `isAutomatedSubmissionSupported`/`validateSupport()` — but registered nothing), `source_policies.automated_application_allowed` is `false` for every row, and no `vacancy_sources` row targets a real employer board yet.

**MP-F1 alone did not unblock `eligibilityGate.ts`'s `verified_facts` gate or `resumeGenerator.ts`'s `generateResumePayload`** — both require a *confirmed* fact (a `fact_confirmations` row with `status = 'confirmed'`). ## Resume fact extraction (MP-F1)

`POST /api/resumes/:id/extract` (`server/index.ts`, logic in `server/resumes/`): `requireAuth` → per-candidate rate limit (`express-rate-limit`, 5 requests / 15 min, keyed by `request.user.id`) → ownership check against `resume_documents` (404 for both "doesn't exist" and "not yours" — never distinguishes) → server-side Storage download → `pdf-parse`/`mammoth` text extraction (`textExtraction.ts`) → OpenAI structured-output extraction (`openaiExtraction.ts`, strict JSON schema + an independent manual validator — never trusts the API response blindly) → `extractFacts.ts` flattens the validated result into `extracted_facts` rows and inserts them in one batch (zero rows ever inserted on any failure, including a malformed-output rejection).

v0 fact vocabulary (code-owned, no PRD taxonomy exists): scalar `full_name`/`email`/`phone`/`location`/`current_title`/`years_of_experience`/`most_recent_employer` (0 or 1 row each); repeatable `skill`/`education`/`experience` (0..N rows each, education/experience flattened to a single string per entry since the table has no way to group multi-field entries). "Never guess": a field the model couldn't determine gets **no row at all**, never a placeholder or a null `fact_value` (the column is `NOT NULL`).

Schema: `20260823090000_extracted_facts_provenance.sql` added `extraction_model`/`extraction_prompt_version` (both `NOT NULL`, no default — safe because the table was verified empty, zero writers, before this migration). Both existing pgTAP fixtures that insert into `extracted_facts` (`extracted_facts_rls.test.sql`, `fact_confirmations_rls.test.sql`) were updated to supply them; the full `supabase test db` suite (29 files, 448 tests) passes against a fresh `supabase db reset` with this migration applied.

New dependencies: `openai`, `pdf-parse` (v2 API — `new PDFParse({data}).getText()`, must `.destroy()`), `mammoth`, `express-rate-limit`. New env vars: `OPENAI_API_KEY` (required, server-only), `OPENAI_MODEL` (optional, defaults to `DEFAULT_OPENAI_MODEL` in `openaiExtraction.ts`).

**No live OpenAI call has been made** — this environment has no `OPENAI_API_KEY` and no outbound network access. Everything is built against an injectable `Pick<OpenAI, "chat">` client (same DI pattern as `serviceClient` in `server/index.ts`) and tested with a mocked client. Real cost/latency/quality against the actual API is unverified until a manual smoke test is run with a real key.

## Fact confirmation (MP-F2)

Closes the gap MP-F1 left open: `extracted_facts` rows existed but nothing ever wrote a `confirmed` `fact_confirmations` row, so `eligibilityGate.ts` and `resumeGenerator.ts` had no real facts to work with. `extracted_facts` remains the immutable extraction-provenance record — candidates never write to it. All candidate action targets `fact_confirmations` only, via candidate-scoped RLS `UPDATE` (no `INSERT` grant on that table for candidates).

**Pending-row creation** (`server/resumes/extractFacts.ts`): since candidates can only `UPDATE` `fact_confirmations`, a `status = 'pending'` row is inserted for every extracted fact at extraction time, service-role-side, in the same request as the `extracted_facts` insert (two separate writes — a torn write here leaves a fact with no confirmation row rather than losing the extraction; reconciling that is out of this phase's scope, same precedent as `reports.ts`'s `submitVacancyReport`).

**Client operations** (`client/src/lib/factConfirmations.ts`): `confirmFact`, `correctFact` (sets `status = 'confirmed'` + `corrected_value`), `rejectFact`, `reopenFact` (all single-row `UPDATE ... WHERE extracted_fact_id = ...`, `.select()`-checked since a zero-row match resolves without a Postgres error), and `confirmAllFacts` (one batched `UPDATE ... IN (...)` for bulk "Confirm all", not N sequential requests).

**Resume generation** (`server/applications/resumeGenerator.ts`): now selects `corrected_value` alongside `extracted_fact_id` from `fact_confirmations`; a confirmed fact's *effective* value is `corrected_value` when non-null, else the original `extracted_facts.fact_value` — a resume must reflect what the candidate actually confirmed, never the raw extraction, when the two differ.

**Client read path** (`client/src/lib/resumeExtraction.ts`): `listExtractedFacts` now does a second query (`fact_confirmations` filtered to the listed fact ids) and joins `confirmationStatus`/`correctedValue` onto each `ExtractedFact`, mirroring the two-step shape `eligibilityGate.ts` and `resumeGenerator.ts` already use server-side. A fact with no confirmation row (should not happen post-MP-F2, defensive only) defaults to `pending`.

**UI** (`client/src/panels/ResumesPanel.tsx`): each extracted fact shows a `StatusBadge` (`fact_pending`/`fact_confirmed`/`fact_rejected`, reusing the existing verified/under-review/blocked color set) plus Confirm/Correct/Reject/Un-confirm actions; "Correct" opens an inline `Input` and shows the original value struck through next to the corrected one once saved. A "Confirm all (N)" button appears per resume when it has pending facts.

**Migration**: `20260823100000_fact_confirmations_corrected_value.sql` adds nullable `fact_confirmations.corrected_value text` (no backfill needed — table was confirmed empty, zero writers, at migration time, same as MP-F1's provenance migration).

**Known limitation — re-extraction creates duplicate pending facts.** Clicking "Extract facts" again on a resume that already has confirmed facts inserts a *new* set of `extracted_facts` rows (and new pending `fact_confirmations` for them); it does not touch or supersede the previously confirmed rows. Both the old confirmed facts and the new pending ones then coexist and both are visible/usable by consumers (`resumeGenerator.ts` includes every *confirmed* fact regardless of which extraction it came from) — there is no dedup, no "supersedes" link, and no UI grouping by extraction run. Reconciling duplicate/stale facts across re-extractions is deferred to a later phase.

**No live OpenAI or Supabase-RLS smoke test has been run for MP-F2** — see `docs/MANUAL_TESTS.md`'s combined MP-F1+MP-F2 smoke test (still the blocking first manual step; unit tests (518 passing) and TypeScript are the only verification performed so far). The `fact_confirmations_rls.test.sql` pgTAP suite was last run and passing in the prior MP-F2 session (per that session's record) — not re-run in this session since no local Supabase/Docker instance was available.

## Role suggestions + selection (MP-R1)

Closes the gap MP-F2 left open on the PRD-journey table: `candidate_selected_roles` (schema+RLS since `20260819090000`) had zero writers anywhere in the repo. No normalized role taxonomy existed in this repository before this phase — three separate migrations (`automation_authorizations`, `candidate_selected_roles`, and `eligibilityGate.ts`'s `role_match` gate comment) independently documented the gap as deliberately deferred; `role_name` is still plain text with no CHECK constraint, matched against `vacancies.raw_title` by case-insensitive substring in `eligibilityGate.ts` — unchanged by this phase.

**Taxonomy** (`client/src/lib/roleTaxonomy.ts`): a static, curated list of 30 entries across 8 categories (Engineering, Data, Product, Design, Marketing, Sales, Operations, Customer/Support), each with `id`/`title`/`category`/`aliases`/`skills`. This is a client-side curation layer only, not a DB-enforced enum — selecting an entry writes its `title` as `candidate_selected_roles.role_name`, so a candidate can still hand-enter/correct any free-text role name that already exists via direct table access (unchanged, matches the migration's stated design). `searchRoles(query)` does case-insensitive substring matching against title and aliases.

**Suggestion engine** (`client/src/lib/roleSuggestions.ts`): `suggestRoles(facts)` filters strictly to `confirmationStatus === "confirmed"` facts (MP-F2's gate — pending/rejected facts are not a reliable signal) and resolves each fact's effective value as `correctedValue ?? factValue`, same rule `resumeGenerator.ts` uses. Primary tier: confirmed `current_title` substring-matches a taxonomy title/alias. Strong tier: same category as a Primary match with ≥2 shared confirmed `skill` facts. Related tier: same category with 1 shared skill, or a different category with ≥2 shared skills (this branch also fires with zero Primary matches — a candidate with confirmed skills but no confirmed title still gets skill-only Related suggestions). Stretch tier is deferred in code comments — no approved signal source (years-of-experience heuristic vs. per-entry seniority tag) yet.

**Data access** (`client/src/lib/candidateSelectedRoles.ts`): `listSelectedRoles`/`selectRole`/`removeRole`, direct-`Supabase`-client writes scoped by `auth.uid() = candidate_id` RLS, same shape and 23505-idempotent-insert pattern as `exclusions.ts` — no Express route needed.

**UI** (`client/src/panels/TargetRolesPanel.tsx`, mounted via `TargetRolesPage`/`App.tsx` now passing `candidateId`/`ready` like every other data-backed page): selected-roles list with Remove, a search box over the taxonomy with Add, and suggestion sections grouped by tier (only tiers with matches render — an empty tier is omitted, not shown empty). Already-selected roles are filtered out of both search results and suggestions.

**No live Supabase-RLS or browser smoke test has been run for MP-R1** — see `docs/MANUAL_TESTS.md`'s new MP-R1 section (same environment blocker as the still-outstanding MP-F1+MP-F2 smoke test). 25 new unit tests plus a full-workspace `npm run typecheck && npm test` (543 tests, all passing) are the only verification performed so far.

## Application worker entrypoint (MP-W1)

Gives the R4/R7 application engine (`planApplication`, `runOneApplicationAttempt`) a real, invocable entry point — before this phase, both were built and unit-tested but nothing anywhere in the repo ever called them; `application_plans`/`application_attempts` could only be created by a test. **No daemon loop or scheduler was added** — inspection confirmed no such pattern exists anywhere in this repo (`server/ingestion/worker.ts` only exports a single claim-and-process function with its own comment stating that scheduling is a later-phase concern, and `server/` has zero `SIGINT`/`SIGTERM` handling anywhere) — so continuous/daemon mode was explicitly scoped out rather than invented from nothing; this phase is single-pass batch mode only.

**Orchestrator** (`server/applications/runner.ts`): `runApplicationBatch(client, options?)` — (1) finds active candidates: `automation_authorizations.status = 'authorized'` intersected with having at least one `candidate_selected_roles` row (two-step query, same style as `evaluateVerifiedFacts`); (2) finds vacancies via `vacancies.trust_status IN ('VERIFIED', 'VERIFIED_INCOMPLETE')` (now `VACANCY_TRUST_ELIGIBLE_STATUSES`, exported from `eligibilityGate.ts` rather than redefined here); (3) calls `planApplication(client, { candidateId, vacancyId })` for every candidate x vacancy pair — deliberately no role-name pre-filter, since `planApplication`'s own `role_match` gate already does that comparison and duplicating it would create a second, driftable copy of the same rule (approved decision); (4) drains `application_attempts` by looping `runOneApplicationAttempt(client)` until it reports `processed: false` or a configurable `maxAttemptsPerBatch` (default 50) is hit.

**Error isolation**: each candidate x vacancy pair is planned inside its own try/catch — a thrown error (an actual infra/query failure; an ordinary ineligible-gate outcome never throws) is `console.error`-logged and collected into `planningFailures`, and the batch continues with the remaining pairs. There's no dedicated DB evidence table for planning-cycle failures (`application_evidence` is per-*attempt* submission evidence, written inside `runOneApplicationAttempt` itself) — this is a deliberate v0 gap, not an oversight. The attempt-drain loop only throws when the `claim_application_attempt` RPC call itself fails (an infra-level failure with no specific attempt to attribute it to, since `runOneApplicationAttempt` already isolates every per-attempt outcome internally and never throws for those) — that case is caught once, logged, and stops the drain for this batch (surfaced as `attemptDrainError` in the result) rather than looping against a broken RPC.

**CLI entrypoint** (`server/applications/cli.ts`, `npm run worker:applications`): constructs a service-role client (`createSupabaseServiceRoleClient`, same DI pattern every other server-side privileged operation uses) since this is system-initiated work, not a request on behalf of one signed-in candidate; runs one batch, prints a structured summary, and exits — no `--watch`, unlike `dev:server`.

**Known limitation — full candidate x vacancy fan-out, not scale-tested.** With no pre-filter, one batch run costs (active candidates) x (verified vacancies) calls to `planApplication`. This is an approved tradeoff for current pre-launch data volumes, not measured against real scale — revisit if either count grows large enough for this to matter.

**No live smoke test has been run for MP-W1** — see `docs/MANUAL_TESTS.md`'s new MP-W1 section (same environment blocker as MP-F1/MP-F2/MP-R1). 9 new unit tests (fully mocked — `planApplication` and `runOneApplicationAttempt` are stubbed, not exercised against a real database) plus a full-workspace `npm run typecheck && npm test` (552 tests, all passing) are the only verification performed so far. Every real candidate remains gated ineligible today regardless — `application_support` (MP-A1 changes what kind of gap this is, see below) and `rate_and_abuse_controls` (still a permanent placeholder) both keep `plansEligible` at 0 against real data.

## Application adapter capability model (MP-A1)

Extends the `ApplicationAdapter` interface (R7-M2) with an explicit capability model, and wires `eligibilityGate.ts`'s `application_support` gate to consult it — but **registers no real source as supported**. Before this phase, `resolveApplicationAdapter` already existed, already resolved every `source_code` to the shared `unsupportedAdapter` fallback, and the gate already identity-compared the resolved adapter against that singleton to decide pass/fail. This phase's actual change is narrow: the gate now asks the adapter `adapter.validateSupport({ vacancy, candidateId })` instead of doing that identity comparison itself — the adapter is now the single source of truth for its own capability, not the gate re-deriving it. **Behavior for every real source_code today is byte-identical to before** — same `NO_ADAPTER_REGISTERED_FOR_SOURCE` reason code, confirmed by every pre-existing `eligibilityGate.test.ts` assertion still passing unchanged.

**Why this phase didn't build what its own brief proposed**: the originating task asked for a *new* `ApplicationAdapter` interface (`sourceCode`/`displayName`/`isAutomatedSubmissionSupported`/`validateSupport()`, `submit()` with no client param) and a `UNSUPPORTED_APPLICATION_SOURCE` reason code — but inspection found the interface, registry, `unsupportedAdapter`, and gate wiring already existed from R7-M2, with a different (and deliberately reasoned) shape: `submit(client, context)` keeps the client because a real adapter needs to read confirmed facts/write mid-submission evidence, and the existing `NO_ADAPTER_REGISTERED_FOR_SOURCE` reason code is already asserted across ~6 tests. Presented this conflict and three explicit decisions were made: (1) extend the existing interface additively rather than replace it — `submit(client, context)` unchanged, new capability fields added alongside; (2) keep the existing `NO_ADAPTER_REGISTERED_FOR_SOURCE` reason code rather than rename it; (3) this phase ships the capability *machinery* only — no source is marked `isAutomatedSubmissionSupported: true`, since no real per-source submission logic or credentials-storage table exists anywhere in this repository to back that claim honestly.

**Interface additions** (`server/applications/adapters/types.ts`): `sourceCode`, `displayName`, `isAutomatedSubmissionSupported: boolean`, and `validateSupport(context: ApplicationSupportContext): ApplicationSupportValidation` (`{ supported: boolean; reasonCode?: string }`), alongside the unchanged `submit(client, context)`. `unsupportedAdapter` (`server/applications/adapters/unsupportedAdapter.ts`) implements the new fields: `isAutomatedSubmissionSupported: false`, `validateSupport()` unconditionally returns `{ supported: false, reasonCode: "NO_ADAPTER_REGISTERED_FOR_SOURCE" }` regardless of the vacancy/candidate passed in, since it represents "no real adapter exists," not a real channel with its own nuance.

**Gate change** (`server/applications/eligibilityGate.ts`): `evaluateApplicationSupport` now takes the full vacancy row (`source_code`/`trust_status`/`raw_title`) plus `candidateId` instead of just `source_code`, resolves the adapter, and builds the `GateResult` from `adapter.validateSupport(...)`'s `{ supported, reasonCode }` — falling back to `NO_ADAPTER_REGISTERED_FOR_SOURCE` when an adapter doesn't supply its own. A passing result now includes `detail: { adapter: adapter.sourceCode }` (previously bare `{ status: "pass" }`, untested since no adapter has ever passed).

**No live smoke test needed** — this gate is a pure function of `vacancies`/adapter state with no external I/O, unlike MP-W1/MP-R1. 8 new unit tests (2 in `unsupportedAdapter.test.ts`, 1 in `registry.test.ts`, 3 in `eligibilityGate.test.ts` using a mocked adapter double via `vi.mock("./adapters/registry.js", ...)` — spying on the real `resolveApplicationAdapter` so every other existing test keeps exercising real resolution — to exercise the pass path, a custom adapter-supplied reason code, and that `validateSupport` receives the right vacancy/candidate context) plus a full-workspace `npm run typecheck && npm test` (558 tests, all passing) are the verification performed. See `docs/MANUAL_TESTS.md`'s MP-A1 section for the regression checklist and the future "when a real adapter is registered" steps.

## Rate & abuse controls (MP-RC1)

**All 8 of PRD §16.1's eligibility gates now have real evaluation logic — the last placeholder is closed.** Before this phase, `rate_and_abuse_controls` was a pure mirror of `automation_authorization` (same reasonCode/detail, no independent query), wired that way in R7-M9 specifically because of a documented R7-M1 founder decision: *"pause/stop-only — no numeric quota, no source-side rate limiting."* MP-RC1 is an explicit, current founder decision that supersedes that specific "no numeric quota" stance — `automation_authorization` remains its own unchanged, separate gate (pause/stop enforcement is unaffected), and `rate_and_abuse_controls` is now a genuinely independent check alongside it, not a replacement for it.

**Rate limit rule** (`server/applications/eligibilityGate.ts`, `evaluateRateAndAbuseControls`): `MAX_DAILY_APPLICATIONS_PER_CANDIDATE = 25` over a rolling `RATE_LIMIT_WINDOW_HOURS = 24` window (not a fixed calendar day). Counts every `application_attempts` status except `cancelled` (an R7-M4 cancellation means the candidate's automation was paused/stopped before submission ever reached a portal — nothing was actually attempted, so it shouldn't count toward abuse prevention). Fails at `count >= 25` (reaching the limit blocks the next attempt, not just exceeding it) with `{ status: "fail", reasonCode: "DAILY_APPLICATION_LIMIT_EXCEEDED", detail: { count, limit, windowHours: 24 } }`; passes with `{ status: "pass", detail: { count, limit } }` otherwise.

**Query shape**: `application_attempts` carries no `candidate_id` column of its own (only reachable via `application_plans.candidate_id`), so this is a two-hop query — every `application_plans` id this candidate has, then every counted-status attempt on those plans within the window — the same "plan → attempts" shape `evaluateIdempotency` already uses, widened from one plan to all of a candidate's plans. Both the status filter and the time-window filter run server-side (`.in("status", ...)`, `.gte("created_at", windowStart)`), so the query stays bounded regardless of a candidate's total history size.

**Test fixture change**: `eligibilityGate.test.ts`'s shared mock now has `application_plans` queried two different, incompatible-looking ways in one `evaluateEligibilityGates` call — `evaluateIdempotency`'s `.maybeSingle()` (single row or null) and `evaluateRateAndAbuseControls`'s bare-await `.eq("candidate_id", ...)` (array). The mock's bare-await path now auto-wraps a non-array `data` into a single-element array (`null` → `[]`, one row → `[thatRow]`), so one `application_plans` override in a test serves both query shapes consistently without any pre-existing idempotency-focused test needing to change — confirmed by every pre-existing test in that file still passing unchanged.

**No live smoke test needed** — same reasoning as MP-A1 (pure function, no external I/O). 8 net-new unit tests in `eligibilityGate.test.ts` (5 obsolete automation_authorization-mirroring tests removed and replaced) plus a full-workspace `npm run typecheck && npm test` (561 tests, all passing) are the verification performed. See `docs/MANUAL_TESTS.md`'s MP-RC1 section for the rate limit rules and manual verification steps.
